## LPの全面リニューアル — EXPERIENCE MOVES BUSINESS(v6.0)

LPを「デザイン会社が制作した水準」まで引き上げるため、**app/page.jsx を全面的に作り直し**ました。
アートディレクション・タイポグラフィ・余白・レイアウト・モーション・人物表現・コピーの見せ方まで設計し直しています。

適用範囲は**LP(`/`)のみ**です。ログイン後のアプリ画面は従来の `lib/theme.jsx` のまま動きます。

### 設計思想

中心思想は **EXPERIENCE MOVES BUSINESS.** — 企業を動かすのは人員ではなく「経験」。
BATTER BOXは人を紹介する会社ではなく、**企業に不足している経験を発見し、流通させるプラットフォーム**として表現しています。

ブランドコピーは「会社に足りない経験を、必要な分だけ。」(説明的)から、
**「その経験に、次の打席を。」**(宣言的)へ変更しました。

### ブランド造形言語 — 「打席」を造形にする

最大の差別化要素は、**BATTER BOXという名前が持つ「打席」のメタファーがこれまでデザインに一切反映されていなかった**点でした。これを共通の造形言語にしています。

- **ホームベースの五角形**: 経験タグの先頭、マーキーの区切り、人物ビジュアルのブロックに使用(`HOME_PLATE_CLIP`)
- **バッターボックスの白線**: Heroの図版を、写真ではなく打席の幾何学で構成
- **ON DECK / NEXT BATTER**: 次のアクションを示す英字ラベル

### デザイントークン(`app/_lp/tokens.js`)

ページごとに場当たり的なCSSを書かず、Color / Typography / Spacing / Container / Radius / Motion / Breakpoints をすべてトークン化し、`app/_lp/LPStyle.jsx` の1ファイルに集約しました。

|---|---|
| Color | WHITE 60〜70% / ORANGE `#F46919` 20〜30% / ニアブラック `#121214` 約10%。グラデーションは使わず単色のベタ面で使用。ネイビーは不使用 |
| Typography | 日本語: Noto Sans JP 900(従来の角丸ポップ体 M PLUS Rounded 1c から変更)／英字: Archivo 800-900 |
| Type scale | `display` clamp(40-100px) / `giant` clamp(34-88px) / `body` 15.5px / `label` 11px(字間0.16em)。**最大と最小で約9倍のジャンプ率** |
| Spacing | セクション余白 clamp(96-200px)、左右 clamp(20-80px)、コンテンツ幅 1440px |

### 主な実装

- **Hero(A+Bハイブリッド)**: ファーストビューは巨大コピー＋打席の幾何学(A案)。`BATTER BOX` → `その経験に、` → `次の打席を。` の順に0.06/0.18/0.32秒で入場。スクロールすると03でAI入力UI(B案)が全面黒で現れる
- **AI EXPERIENCE**: 入力欄にプレースホルダーが1文字ずつタイプされ(触ると停止)、`Analyzing...` → 経営課題タグ → NEEDED EXPERIENCE 01/02/03 → MATCHED、の4段で結果が展開します。**LP上のデモである旨を画面に明記**しています
- **地色に追従するヘッダー**: スクロール位置の直下にあるセクションの地色を検出し、白/黒/オレンジに切り替わります。**濃い地色の上ではロゴ画像を白の英字ワードマークに差し替え**ます(白抜き版ロゴがないため)
- **HOW IT WORKS**: 4枚のカードを横並びにせず、左のレールが現在地を示しながらスクロールで01→04と進みます
- **TWO SIDES**: ホバーで領域が広がるインタラクション
- **モーション**: すべて `prefers-reduced-motion` で停止します

### 人物表現

**現時点で人物写真の素材がないため**、写真の位置にブランド造形(ニアブラック/オレンジの面＋ホームベースの五角形＋経験の見出し)を配置しています。単なるグレーのプレースホルダーではなく、それ自体が成立する造形にしました。

`public/people/01.jpg` 〜 を置き、`app/_lp/tokens.js` の **`PEOPLE_PHOTOS_READY` を `true`** にすると写真表示に切り替わります(false の間は404リクエストを出しません)。

「誰なのか」より「何を経験したのか」を主役にする方針で、`売上 0→10億` `新規事業 3回` `IPO 経験` `海外 5カ国展開` を最も大きく、氏名・職種はその下に小さく置いています。

### 実装中に見つけて直したバグ

ビルドが通っても壊れている箇所があったため、**実際にサーバーを起動しブラウザで描画して検証**しました。

1. **サーバー/クライアント境界違反**: サーバーコンポーネントから `"use client"` モジュールの色オブジェクトを import しており、ページが500エラーで落ちていました(ビルドは成功していた)。色は `tokens.js` から直接読むよう修正
2. **ハイドレーション不一致**: `<style>{\`...\`}</style>` の形でCSSを渡すと、Reactが `'` を `&#x27;` にエスケープするためサーバーとクライアントでテキストが一致せず、毎回コンソールにエラーが出ていました。`dangerouslySetInnerHTML` に変更。**同じ欠陥が `lib/theme.jsx` の `GlobalStyle` にもあったため、こちらも修正しています**(見た目は変わらない純粋なバグ修正)
3. **Heroがヘッダーに潜り込む**: インラインの `paddingTop: 0` がCSSを上書きしていました
4. **ヘッダーの自己参照**: 地色検出の走査対象にヘッダー自身が含まれ、値が固定されていました
5. **日本語の孤立文字**: 巨大タイポに対して容器幅の上限が狭く、「い。」「だ。」が単独で改行されていました。容器の上限を外し `line-break: strict` を追加

検証結果: 横方向のはみ出し **0px**(デスクトップ1440・モバイル390の両方)、コンソールエラー **0件**。

### 正直な注記

- **人物写真が入るまで「人の温度」は出ません。** 造形で代替していますが、チェック項目の「人の温度を感じるか」は写真が入って初めて満たされます。登録者本人の写真を10枚ほどいただければ、`PEOPLE_PHOTOS_READY` を切り替えるだけで反映されます
- **サンドボックス環境ではGoogle Fontsが証明書エラーで読み込めなかったため、検証時のスクリーンショットは指定フォント(Noto Sans JP / Archivo)ではなく代替フォントで描画されています。** レイアウトの検証はできていますが、**実際の字面はデプロイ後に確認してください**
- **適用範囲はLPのみです。** 新規登録画面・会社概要・利用規約などは従来のデザインのままなので、LPから登録に進んだ瞬間に世界観が切り替わります。ご指示どおりの範囲ですが、ブランド体験としては継ぎ目が残ります
- **実績数値・導入企業ロゴ・導入事例は入れていません**(架空の数字になるため)。これらが入ると説得力は大きく変わります
- 人物の氏名はイニシャル表記とし、「登録されている経験の例です」と明記しています
- このバージョンもビルド・自動テスト(全130件パス)・ローカルでの描画検証までの確認で、**Vercel上での実動作確認は行っていません**

## ダッシュボード刷新・法務文書の正式版化・対話の短縮(v5.5)

### ① アプリ画面のヘッダーを固定表示(人材①)

`.app-topbar` というクラス名は使われていたものの、**対応するCSSがどこにも定義されておらず**、ヘッダーは通常のブロック要素としてスクロールで流れていました。`position: sticky` で上部に固定し、ロゴを左・操作（デスクトップはナビ＋ログアウト、モバイルはログアウトのみ）を右に配置しています。半透明＋背景ぼかしで、下のコンテンツが透けて見えます。

- モバイルではロゴを32pxに縮小し、ノッチ（`env(safe-area-inset-top)`）を考慮
- **注意点**: `position: sticky` は祖先に `overflow-x: hidden` があると効きません（その祖先がスクロールコンテナ扱いになるため）。`.app-root` がまさにその状態だったので、`overflow-x: clip`（スクロールコンテナを作らない）を後置で追加しています。未対応の古いブラウザ（Safari 15以前など）は従来どおり `hidden` にフォールバックし、その場合ヘッダーは固定されません

## マッチ度計算式の再設計(v4.4)

v4.3の調査で判明した、より根本的な問題への対応。

- 旧式のMATCH%は10軸全体の加重平均だったため、**1〜2軸に強い「専門家型」の人材が構造的に20%台に留まり、30%の足切りにほぼ全員が引っかかっていた**。例: 営業が深刻な課題の企業 × 営業28/30点の専門家 → 旧式では約24%。19名の実在人材が登録されていても誰も表示されなかった直接の原因。
- 新式は「**企業の課題TOP3(学習係数込みで深刻な軸の上位3つ)に対する人材の強さの加重平均**」。課題と無関係な軸が弱くてもスコアは下がらない。月10時間で課題TOP3を埋めるという商品設計と一致する。上の例は新式で約67%になる。
- 課題と噛み合わない人材(例: 営業課題の企業×tech専門家)は従来どおり30%未満で足切りされる。この性質をテストで固定(tests/matching.test.js に2件追加、計67件)。
- 学習係数(AxisPerformance)は軸の選定と重み付けの両方に効き続ける。フェーズ一致ボーナス(+6)も従来どおり。

### 正直な注記

- スコアの絶対値の意味が変わるため、v4.3以前に画面で見たMATCH%とは連続性がない。ベータ公開前に導入すれば実ユーザーへの影響はない。
- 「課題TOP3に対する強さ」という定義は、UIの説明文(MATCH%の内訳)と将来ずれないよう注意すること。

## マッチ候補ゼロ問題の修正(v4.3)

本番テストで「最適な人材が出ない」というフィードバックを受けた対応。

- 従来はマッチ度30%未満の候補を一律非表示にしていたため、登録人材・登録企業がまだ少ない時期には**候補が1件も表示されない**ことがあった。
- 30%以上の候補がゼロの場合は、上位3件を「参考」として表示するフォールバックを追加(`lowMatchFallback`)。企業→人材(/api/match/company)と人材→企業(/api/match/talent)の両方向に適用。
- UIには「適合度30%以上の人材(企業)はまだ登録されていません。近い順に参考として表示しています」という正直な注記バナーを表示する。高く見せかけるのではなく、少ない母数の中での相対順位であることを明示する方針。

### 正直な注記

- 根本的な解決は登録人材を増やすこと。ベータ初期は運営側で最低10〜20名の実務経験者に登録してもらうのが望ましい。
- サンプル人材3名は実在しないため、ベータ公開前に削除し、実在の登録者と入れ替えること。

## AI応答の高速化・自動リトライ(v4.2)

本番テストで「AIの応答が遅い」「再試行が何度も出る」というフィードバックを受けた対応。

- **対話の高速モデル化**: 企業診断・人材自己分析の対話1問1問と軸の深掘りを、高速モデル(claude-haiku-4-5)に切り替えた。体感速度は3〜5倍。最終的な10軸スコアリング・分析は従来どおり高精度モデル(claude-sonnet-5)を使い、診断品質は維持する。モデルは環境変数 `CLAUDE_MODEL` / `CLAUDE_FAST_MODEL` で差し替え可能。
- **サーバー側の自動リトライ**: `lib/claude.js` に、一時的な失敗(429レート制限・529過負荷・5xx・ネットワーク断)を最大2回まで自動でやり直す処理を追加。ユーザーに「再試行」ボタンが表示される頻度を大きく減らす。
- **タイムアウト上限の明示**: AI呼び出しを含む12のAPIルートすべてに `export const maxDuration = 60` を追加し、Vercelが処理を途中で打ち切らないようにした。

### 正直な注記

- 高速モデルへの切り替えで対話の質問文の質がわずかに変わる可能性がある。本番で数回対話を回し、質問の自然さに問題がないか確認するのが望ましい。
- 自動リトライはAPIキー未設定・認証エラー(401)など「待っても直らない」エラーには発動しない(即座にエラーを返す)。

## 管理画面の通知バッジ・メール通知の拡充(v4.1)

「管理画面で新着メッセージ・契約等の動きが分かりやすいようにしたい」「メールも届くようにしたい」との要望に対応しました。

### 管理画面のナビゲーションに赤い通知バッジ
`AdminNav`を非同期コンポーネント化し、以下の件数を取得してナビゲーション項目に赤く光る(パルスアニメーション付き)バッジで表示するようにしました。

- 「マッチング」: 人材の回答待ちの契約提案件数(`Engagement.status === "proposed"`)
- 「メッセージ」: 直近24時間以内に送信されたメッセージ件数
- 「問い合わせ」: 未対応の問い合わせ件数(`status === "new"`)

**注記**: 「メッセージ」の件数は、まだ既読管理の仕組みがないため、「直近24時間以内の新着」という簡易な基準にしています。将来的に「最終閲覧日時」のような正確な既読管理をするには、別途設計が必要です。

### メール通知の対象を拡大
以前(v3.8)は新着メッセージ・パスワード再設定のみでしたが、以下にも拡大しました。

- **契約条件の提案時**: 人材へ、提案内容(稼働時間・金額)を通知
- **契約への回答時**: 企業へ、承諾/辞退の結果を通知
- **新しい問い合わせの受付時**: 全ての管理者アカウントへ、問い合わせ内容を通知

いずれも、送信に失敗しても本体の処理(契約提案・回答・問い合わせ受付)は継続する設計です。**実際にメールが届くようにするには、引き続き`RESEND_API_KEY`をVercelの環境変数に設定する必要があります**(v3.8参照)。まだ設定していない場合は、これらのメールも「コンソールログに出力されるだけ」の状態のままです。

## 契約条件のAI提案(v4.0)

「契約条件のパターンをAIで複数出すのはどう?」という提案を受け、実装しました。

企業が「契約条件を提案する」フォームを開いた際、「AIに提案してもらう」ボタンから、診断結果の課題の優先度・対象人材の役職と経験年数・企業の年商規模をもとに、**「お試し導入」「標準」「本格導入」の3パターン**(月間稼働時間・企業支払額・一言の理由)をAIに生成させ、クリックした内容がそのままフォームに反映されるようにしました(その後も自由に編集できます)。

- `lib/contractSuggestionPrompts.js`: 提案生成用のプロンプト
- `POST /api/matches/[matchId]/suggest-contract-terms`: 企業アカウントのみ実行可

**重要な設計判断**: このプラットフォームには、まだ実際の成約金額の蓄積データがありません。そのため、AIが提示する金額は「一般的な感覚に基づくたたき台」であり、実際の相場を反映したものではありません。これを隠さず、提案が表示されるたびに「実際の成約相場データがなく、あくまで参考値」という注記を必ず表示するようにしています。将来的に実際の契約データが蓄積されれば(データを競合優位性に変える仕組み・AxisPerformanceと同様の考え方で)、より精度の高い提案に育てられる余地があります。

## 契約フローを企業起点に再設計(v3.9)

「契約は人材側ではなく企業側から送れるようにして、契約に進んだ後、内容確認・委託契約書を締結・プロジェクト進行の流れにしたい」との要望を受け、契約成立までの流れを作り替えました。

### 変更前
v3.5で実装した「企業・人材どちらからでも“契約に進みたい”と意思表示でき、双方揃ったら運営が手動で契約条件を入力して成立させる」という、運営が仲介する双方向の仕組みでした。

### 変更後(企業起点の一方向フロー)
1. **企業が契約条件を提案する**: メッセージ画面から、月間稼働時間・月額(企業支払額)を入力して送信(`POST /api/matches/[matchId]/propose-contract`、企業アカウントのみ実行可)。人材への支払額は標準料率(60%)を目安に自動計算されるが、個別に指定も可能
2. **人材が内容確認・回答する**: 提案された条件がメッセージ画面に表示され、「承諾する」「辞退する」を選べる(`POST /api/matches/[matchId]/respond-contract`、人材アカウントのみ実行可)。辞退した場合は提案が削除され、企業は条件を変えて再提案できる
3. **承諾後、契約成立・プロジェクト自動開始**: 承諾すると同時に、契約(Engagement)が正式に成立し、稼働時間の加算、企業⇄人材で共有するプロジェクトの自動作成までを1つのトランザクションで実行する
4. **委託契約書の内容確認**: 新規`/app/contracts/[engagementId]`ページで、甲乙・契約形態・対象課題・稼働時間・報酬額等をまとめた「業務委託契約 内容確認書」を、契約成立後いつでも確認・印刷/PDF保存できるようにした

### 運営(管理画面)の役割の変化
運営が毎回契約条件を手動入力する必要はなくなり、企業・人材の間で完結するセルフサービス型の流れになった。ただし、以下は維持している。

- 管理画面から手動で契約を成立させる機能(`acceptMatchAction`)は、緊急時のフォールバックとして残した(企業が既に提案中の契約がある場合でも安全に上書きできるよう修正済み)
- `/admin/matches`・企業/人材の詳細ページ・`/admin/messages`に、「人材の回答待ちの契約提案」件数・バッジを表示し、運営が状況を把握できるようにしている

### 削除した旧機能
v3.5で追加した「双方が契約に進みたい意向を示す」ボタン(`Match.companyReadyAt`/`talentReadyAt`)による仕組みは、この新しいフローに置き換わったため、UI・APIエンドポイント(`/api/matches/[matchId]/ready`)を削除した。データベースのカラム自体は(移行リスクを避けるため)残しているが、今後使用しない。

**重要な注記(法的な位置づけについて)**: 「委託契約書を締結」という言葉を使っていますが、実装したのは電子署名等による法的拘束力のある契約締結ではなく、**プラットフォーム上で合意した契約条件を記録・確認できる画面**です。確認書の画面にもその旨を明記しています。正式な契約書面が必要な場合は、以前作成した契約書ひな形(docx)を用いて別途締結することを想定しています。この点はビジネス上・法務上の判断が必要な部分だと思いますので、実際の運用前に確認いただくことをおすすめします。

**正直な注記(動作確認について)**: この一連の変更は、企業側・人材側それぞれのアカウントを使って実際に「提案→承諾→契約成立→プロジェクト開始」まで通しで動かした確認はできていません。特に、既に契約が成立している状態から人材が辞退した場合の挙動(現状は起こり得ない導線ですが)や、企業が同じ相手に再提案する場合の表示更新のタイミングは、実際に触ってみないと分からない部分です。

## メッセージのメール通知(v3.8)

「メッセージがあると、登録のメールアドレスに通知がいくようにしたい」との要望に対応しました。あわせて、これまで「ログ出力のみ」で未実装だったパスワード再設定メールも、同じ仕組みで実際に送信されるようにしています。

### 実装内容
- `lib/mailer.js`: [Resend](https://resend.com)のAPIを直接fetchで呼び出す送信ヘルパー。追加のnpmパッケージは不要(Anthropic APIの呼び出し方と同じ考え方)
- `lib/siteUrl.js`: メール本文内のリンクを常に絶対URLで組み立てるためのヘルパー(`NEXT_PUBLIC_SITE_URL` → `VERCEL_URL` → ローカル用フォールバックの優先順位)
- `POST /api/messages`にメール送信を追加。新しいメッセージが送られると、**受信側(相手)の登録メールアドレス**に、送信者名・本文の冒頭・ログインリンクを含む通知メールを送るようにした
- `POST /api/auth/forgot-password`も同じ仕組みで実際にメールを送るように変更(これまでの「ログ出力のみ」から置き換え)
- メール送信に失敗しても、メッセージの送信・パスワード再設定リクエスト自体は失敗させない(通知は「あれば嬉しい」機能であり、本体の動作を止める理由にはしないという考え方)

### 実際にメールを送るために必要な追加設定

**`RESEND_API_KEY`を設定しない限り、これまで通りコンソールログに出力されるだけで、実際のメールは送信されません。** 実際に送るには、以下の設定が必要です。

1. [resend.com](https://resend.com)で無料アカウントを作成
2. ダッシュボードでAPIキーを発行
3. Vercelのプロジェクト設定 → Environment Variables に `RESEND_API_KEY` としてそのキーを追加
4. (任意)独自ドメインをお持ちの場合、Resend側でそのドメインを認証すると、`EMAIL_FROM`にそのドメインの送信元アドレス(例: `notify@batterbox.jp`)を設定できます。認証していない場合は、Resendのテスト用アドレス(`onboarding@resend.dev`)がデフォルトで使われます
5. Vercelで再デプロイ(環境変数の追加だけでは反映されないため、Redeployが必要です)

**正直な注記**: 現状は、メッセージが送られるたびに毎回通知メールが送信される設計です。短時間に何度もやり取りが続く場合、通知が頻繁に届いて煩わしく感じられる可能性があります。将来的に「一定時間まとめて1通にする」といった調整が必要になるかもしれません。また、この機能一式は実際にResendと接続して送信を確認したことがなく、Resend側のAPIレスポンス形式が実際に想定通りかも未検証です。

「企業も人材もやり取りしているDMが一元管理できる状態にしたい」との要望に対応しました。v3.3で個別のメッセージ閲覧ページ(`/admin/matches/[matchId]/messages`)は作りましたが、そこにたどり着くには企業ページ・人材ページから該当のマッチングを探して開く必要があり、「全体を俯瞰する場所」がありませんでした。

- 各行に、最終メッセージのプレビュー(送信者・本文の先頭)・メッセージ件数・「双方合意済み・要対応」バッジ(v3.5で追加した契約意向表明の状態)を表示。クリックすると個別のメッセージ閲覧ページ(読み取り専用、運営は送信不可)に遷移する

## 人材の新規登録を自動承認に変更(v3.6)

「人材も企業も管理側で承認するフローになっているが、機能を残したまま基本は承認の状態にしてほしい」との要望を受けて対応しました。

**まず、正確な現状の共有です**: 実は承認フローが存在していたのは**人材側のみ**でした。企業側には元々承認の仕組み自体がなく、企業アカウントは登録後すぐに診断・利用が始められる設計でした。

人材側について、以下のように変更しています。

- `Talent.status`のデフォルト値を`"pending"`(審査中)→`"approved"`(承認済み)に変更。新規登録した人材は、これまで管理者が手動で「承認」ボタンを押すまでマッチング候補に出てこなかったが、今後は登録直後から候補に表示されるようになる
- **承認・却下の機能自体は削除せず維持**。これまでは「審査中(pending)」の人材にしか承認/却下ボタンが表示されなかったが、今後は**承認済みの人材にはいつでも「却下」ボタンを、却下済みの人材にはいつでも「承認」ボタンを表示**するようにした(状態に関わらず、いつでも管理者が判断を切り替えられる)
- `/api/talent/analyze`・`/api/talent/dialogue/answer`(スキル解析・自己分析対話の完了時にDB保存する処理)の内部フォールバック値も、新しいデフォルトに合わせて変更

これにより、通常運用では人材登録のたびに承認作業をする必要がなくなりつつ、問題のある人材が現れた場合に管理画面からいつでも除外できる機能は維持されています。

## メッセージ後の「次にどう進めるか」フローを明確化(v3.5)

「企業と人材がメッセージでやりとりした後、具体的にどう進めるかのフローが確立されていない」という指摘に対応しました。これまでは、メッセージを送り合った後の展開が完全にブラックボックス(運営が裏で個別に動くこと前提)になっており、企業・人材のどちらにも「次に何をすればいいか」が見えていませんでした。

### 「契約に進みたい」の意向表明

## 対話の実運用フィードバック対応(v2.9)

実際に使ってみた結果を踏まえて、対話の速度・完了バグ・トーン・情報の見やすさを一通り見直しました。

### 15問で診断結果に進めなくなるバグの修正
`callClaudeJSON`が用途によらず`max_tokens: 2000`固定だったため、対話ターン数を15に増やした結果、対話ログが長くなり最終スコアリング(10軸のscores・axisNotes・topIssueDetails・summaryを一度に出力)がその上限を超えて打ち切られ、JSONが壊れることがありました。`max_tokens`を呼び出し側で指定できるようにし、1問ごとの質問生成は700(体感速度向上も兼ねる)、最終スコアリングは3500に分離しました。

- 質問数を15→10に変更(`MAX_DIALOG_TURNS`、フロント/バックエンド両方)
- 回答の選択肢を3択→4択に変更

- `Company`モデルに`fundingType`(`independent` | `vc`)フィールドを追加し、DBに保存。企業設定画面(`ProfileFieldsCompany`)でも同様に選択可能

## 未ログインでも診断・スキルマップ作成を始められる導線(v2.5)

以前は、ランディングページのCTAを押すと必ず`/signup`(企業/実務経験者を選ぶ新規登録画面)に行き、そこでアカウントを作ってから初めて診断が始まる流れでした。「無料で会社を診断する」を押したのに新規登録画面が出て、しかも関係ない「実務経験者として登録」の選択肢まで見える、という分かりにくさがありました。

これを、**先に無料で診断・スキルマップ作成を体験してもらい、最後にアカウント作成(=そのままログイン)という順番**に変更しました。

- `/diagnose` — 未ログインで進められる企業向けAI課題診断。会社情報入力→AI対話→Growth Map表示→最後にメールアドレス・パスワードを入力してアカウント作成、の4ステップ
- `/join` — 未ログインで進められる実務経験者向けスキルマップ作成。経歴入力→AI解析→スキルマップ表示→アカウント作成、の4ステップ
- ランディングページの「無料で会社を診断する」「無料でAI課題診断を受ける」は`/diagnose`へ、「人材として登録する」「無料でスキルマップを作る」は`/join`へリンクするよう変更(ヘッダーの汎用的な「無料で始める」ボタンのみ、従来通り`/signup`の選択画面のまま)
- 最後の「アカウント作成」ステップで入力したメールアドレス・パスワードは、そのままログイン情報として使われる(`/api/auth/signup`でアカウント作成→即座にセッションが張られ、`/app`にログイン済みの状態で遷移する)

**実装の考え方**: `/api/diagnosis/start`・`/api/diagnosis/answer`・`/api/talent/analyze`は、認証を必須ではなくした(未ログインでもAI診断自体は進められる)。ただし未ログイン中は診断結果をDBに保存せず、ブラウザ側(React state)に保持しておくだけにしている。診断が完了しアカウントを作成したタイミングで、新設した`POST /api/diagnosis/claim`・`POST /api/talent/claim`が、保持していた診断結果をまとめてそのアカウントに保存する。企業/実務経験者アカウントで既にログインしている場合の挙動(その場で都度保存する、再診断は履歴として積み上がる等)は変更していない。

`/diagnose`・`/join`のUIは、既存の`/app`内のStepコンポーネント(`StepCompany`・`StepDialog`・`StepSkillMap`等)をそのままexportして再利用しており、UIロジックの二重管理を避けている。

## 認証

- 企業ユーザー・実務経験者ユーザーは `/signup` で自分でアカウントを作成します(メール+パスワード、パスワードはNode組み込みのscryptでハッシュ化。追加ライブラリなし)。
- 管理者アカウントは公開のサインアップ画面がなく、`prisma/seed.js` 経由でのみ作成されます(意図的な設計です)。
- セッションはDBに保存し、httpOnly Cookieでトークンだけをブラウザに渡す方式です。
- 診断・解析・マッチングの各APIは、クライアントが送ってくる`companyId`/`talentId`を信用せず、セッションから取得したアカウントの持ち主情報を使います。同じアカウントで再度診断/解析すると、新しいCompany/Talentを作らずに既存プロフィールを更新し、スキルマップだけ履歴として追加します。

## メッセージ機能(企業⇄実務経験者のDM)

マッチング候補一覧の「メッセージを送る」ボタンを押すと、`/api/matches/connect` がその組み合わせの`Match`を作成(または既存のものを再利用)し、メッセージスレッドを開きます。スレッドは5秒間隔でポーリングして更新します(WebSocketは未導入)。ヘッダーの「メッセージ」ボタンから、自分が関わっている全スレッドの受信箱にアクセスできます。アクセス制御は、そのMatchの企業側/人材側どちらかのアカウント本人(または管理者)のみに限定しています。

## 足切りフィルター(稼働上限)

`Capacity.maxConcurrentEngagements`(デフォルト3社)に対して、進行中(`status: active`)の契約数が上限に達している人材は、マッチング候補(`/api/match/company`)から自動的に除外されます。契約が成立すると `Capacity.currentCommittedHours` に稼働時間が加算され、契約が一時停止・完了になると解放されます。

`/legal/terms`(利用規約)と `/legal/privacy`(プライバシーポリシー)を用意しています。弁護士レビュー・関連ドキュメントの整備は完了している前提として扱っています。

## データを競合優位性(モート)に変える仕組み(v1.0)

「データを蓄積するほど、競合が同じサービスを作っても追いつけない」状態を目指し、蓄積データをマッチング精度の向上に実際にフィードバックする仕組みを実装しました。

- **`AxisPerformance`モデル**: 各軸(10軸それぞれ)について、その軸が「一致軸」として採用されたマッチングの平均成果スコア(`EngagementOutcome`)を集計し、学習係数(0.7倍〜1.3倍)を算出します
- **`lib/learning.js`**: 学習係数の計算ロジック(外部依存なし、純粋関数としてテスト可能)。サンプル数が3件未満の軸は中立値(1.0)のまま据え置き、少数データでの過学習を防ぎます。サンプルが増えるほど、算出された係数に近づく設計(ベイズ的な縮小)です
- **`scoreMatch()`への統合**: `lib/matching.js`のスコア計算式に、学習係数を重み付けとして組み込みました。既存の呼び出し(係数省略時)は従来と全く同じ結果を返すため後方互換です
- **`/admin/insights`**: 軸ごとの学習係数、フェーズ別の平均スコア傾向などを確認できる画面。「学習係数を再計算する」ボタンで、蓄積された成果データから再計算できます(スケジューラは未導入のため手動トリガー)

この仕組みは、実際の成果データ(`EngagementOutcome`)が蓄積されるほど精度が上がっていく設計になっています。同じ計算式を真似ただけの競合が現れても、BeFreeと同じ量の実績データを持たない限り、同じ精度のマッチングは再現できません。

## ナビ出し分け・実URLルーティング・評価・AIプロフィール改善案(v2.2)

未着手として残っていた項目のうち、⑬・企業からの評価・AIプロフィール改善案に対応しました。

### ⑬ ログイン状態別のグローバルナビゲーション出し分け

ランディングページのヘッダーをサーバーコンポーネント化し(`getCurrentUser()`をサーバー側で呼ぶため、クライアント側フェッチによる表示のちらつきがありません)、以下のように出し分けています。

- 未ログイン: お問い合わせ / ログイン / 無料で始める
- 企業・実務経験者としてログイン中: 「〇〇さん、おかえりなさい」+ ダッシュボードへのリンク
- 管理者としてログイン中: 管理画面へのリンク

### `/app/projects/[id]` の実URLルーティング

これまでプロジェクト詳細は`app/app/page.jsx`内のSPA的な画面切り替え(`view`状態)でのみ表示され、URLを直接共有・ブックマークできませんでした。`app/app/projects/[id]/page.jsx`として独立した実URLページを新設し、同じAPI(`/api/projects/[id]`等)を使って同等の機能(タスク・KPI・稼働ログ・コメント・90日プラン・AI月次レビュー・評価)を提供します。

既存の巨大なSPAファイルへの変更リスクを避けるため、コンポーネントを共有するのではなく独立した実装にしています(表示内容は基本的に一致しますが、コードは重複しています)。プロジェクト一覧の各カードに「共有可能なURLで開く」リンクを追加しました。

### 企業からの評価

新規モデル`TalentRating`(プロジェクト単位で1件、企業側のみ記録・更新可)。`POST /api/projects/[id]/rating`で1〜5の星評価とコメントを送信できます。人材ダッシュボードに平均評価が表示されます。

### AIによるプロフィール改善案

`lib/profileSuggestion.js`・`POST /api/talent/profile-suggestion`。現在の自己紹介・役職・スキルマップ上の強みをもとに、AIが3〜4個の具体的な改善提案を生成します。人材ダッシュボードの「改善案を生成」ボタンから、都度生成する方式です(保存はしません)。

- **自動テスト** — `tests/`配下。Node.js組み込みの`node:test`を使用(追加パッケージ不要)。`npm test`で実行できます。マッチングロジック(`lib/matching.js`)とパスワードハッシュ(`lib/passwordHash.js`)を対象に、このプロジェクト内で初めて実際に実行して合格を確認したテストです(18件、全件成功)

上記はいずれも「最初の実ユーザーを迎える前にやっておきたい」水準のものです。CI/CD・権限の細分化・DBバックアップ体制・決済の自動化・J-SOX内部統制・外部監査などは、まだ先のフェーズとして残っています。

## 支払いフローと契約構造

支払いは「企業 → BeFree → 人材」の流れを前提としています。企業ユーザーと実務経験者ユーザーの間に直接の契約関係はなく、代わりに以下の2本の契約として扱います。

- **企業 ⇄ BeFree**: 企業がBeFreeに業務委託料を支払う(`Invoice`)
- **BeFree ⇄ 人材**: BeFreeが人材に業務委託料を支払う(`Payout`)

`Engagement`(契約)は、この2本の金額(`companyAmount` / `talentAmount`)を保持し、その差額がBeFreeの取り分になります。標準手数料率は`lib/pricing.js`の`BEFREE_FEE_RATE`(40%)で確定しており、「人材支払額 = 企業請求額 × 60%」が標準です。個別契約で例外的な料率にしたい場合は、金額を直接入力して調整できます。管理画面の「契約にする」フォームで両方の金額を入力し、`/admin/engagements`でそれぞれ独立して請求・支払いのステータスを管理できます。契約書のひな形も、企業⇄BeFree用・BeFree⇄人材用の2種類を別途用意しています(このリポジトリには含まれません)。

## お問い合わせ機能

`/contact` に公開の問い合わせフォームを設置しました(認証不要)。送信内容は`Inquiry`としてDBに保存され、`/admin/inquiries`で確認・ステータス管理(未対応/返信済み/対応完了)ができます。外部のメール送信サービスとは連携していないため、新着の通知は現状「管理画面を見に行く」運用です。

企業/人材の詳細ページにある「提案として記録」ボタンでMatchレコードが作成され、「契約にする」で業務委託のEngagementに格上げされます。管理画面の操作はすべてServer Actionsで実装しており、各Actionの冒頭で`role=admin`を再検証しています(ページの認証ガードを迂回されても安全なように)。

## Web公開の手順(ターミナル不要・ブラウザだけで完結)

以前は「データベースの初期設定」にターミナル操作(`npx prisma db seed`)が必要でしたが、v1.1で見直し、**すべてブラウザの操作だけで公開できる**ようにしました。順番に進めてください。

### ① コードをGitHubにアップロードする

このzipを展開し、中身(`app`フォルダや`package.json`など)をGitHubリポジトリにアップロードしてください。GitHub上で空のリポジトリを作成し、「uploading an existing file」からドラッグ&ドロップでアップロードできます(ターミナル不要)。

既にリポジトリがある場合は、今回のzipの中身で上書きアップロードしてください(前回アップロードした時点よりもかなり機能が増えています)。

### ② データベースを用意する(Neon推奨)

1. [neon.tech](https://neon.tech) でアカウントを作成(無料枠があります)
2. 新しいプロジェクトを作成すると、接続文字列(`postgresql://...`から始まる長い文字列)が発行されます。これをコピーしておいてください

### ③ Vercelでプロジェクトを作成する

1. [vercel.com](https://vercel.com) で「Add New Project」→ ①でアップロードしたGitHubリポジトリを選択
2. **デプロイボタンを押す前に**、「Environment Variables」の欄に以下を追加してください

| Key | Value |
|---|---|
| `ANTHROPIC_API_KEY` | Anthropicコンソールで取得したAPIキー |
| `DATABASE_URL` | ②でコピーしたNeonの接続文字列 |
| `SETUP_KEY` | 自分で決めた適当な英数字の文字列(合言葉。次の④で使います) |
| `SEED_ADMIN_EMAIL` | 管理者としてログインしたいメールアドレス(任意。未設定でも動きます) |
| `SEED_ADMIN_PASSWORD` | 管理者パスワード(任意。未設定だと自動生成されます) |
| `RESEND_API_KEY` | メール通知(後述)を実際に送る場合のみ必要。未設定でも他の機能はすべて動きます |
| `EMAIL_FROM` | 通知メールの送信元アドレス(任意。未設定時は`onboarding@resend.dev`が使われます) |

3. 「Deploy」を押す

デプロイ中に、データベースのテーブルが自動的に作られます(以前は別途コマンド実行が必要でしたが、ビルド時に自動実行されるようにしました)。

### ④ 初期データを投入する(ブラウザで1回だけアクセス)

デプロイが完了したら、発行されたURLの末尾に `/api/setup?key=あなたが決めた合言葉` を付けてブラウザで開いてください。

例: `https://befree-app-xxxx.vercel.app/api/setup?key=your-secret-here`

これだけで、管理者アカウントとサンプルデータ(候補人材3名・候補企業3社)が作成されます。`SEED_ADMIN_PASSWORD`を設定していなかった場合は、この画面にランダム生成されたパスワードが表示されるので、**必ずその場でコピーして控えてください**(二度と表示されません)。このURLは何度開いても安全です(既にセットアップ済みなら何もしません)。

### ⑤ 動作確認

1. 発行されたURL(例: `https://befree-app-xxxx.vercel.app`)を開く → ランディングページが表示されるはずです
2. `/login` から、④で確認した管理者アカウントでログイン → `/admin` に入れるか確認
3. トップページから「企業として無料で診断を受ける」を試し、AIとの対話が実際に動くか確認

これで公開は完了です。うまくいかない箇所があれば、どの手順で・どんな画面が出たかを教えてください。
